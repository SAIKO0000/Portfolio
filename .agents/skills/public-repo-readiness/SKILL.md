# Public Repo Readiness

Treat every linked repository as part of the hiring portfolio. Review read-only by default; edit, publish, change visibility, or rewrite history only when the user explicitly requests it.

## Audit

- Confirm repository identity, visibility, default branch, description, topics, homepage, license decision, and social preview.
- Verify README claims against the code and runnable behavior. Document prerequisites, setup, architecture, current limitations, and demo data truthfully.
- Check public links, screenshots, relative asset paths, badges, contact information, and legacy project names.
- Confirm team size and Mark's contribution without inflating ownership.
- Search for secrets, credentials, participant-identifying data, private URLs, generated clutter, and files that should remain local.
- Prefer real approved screenshots and diagrams. Label simulations or re-enactments; do not fabricate product imagery or metrics.
- Run the repository's existing checks when requested or necessary to substantiate readiness.

## Result

Return a severity-ordered report with: blockers before linking, important credibility repairs, optional polish, and verification evidence. A repository is ready only when a visitor can understand what it does, what Mark contributed, how to evaluate it, and which limitations remain.

For Relay, retain the public product name “Relay” while documenting any unavoidable legacy technical identifiers accurately. Do not make unrelated application-code changes during a documentation and asset cleanup.
